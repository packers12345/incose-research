  --- logan_fegenbush_lanl ---
    What capabilities would you be interested in 
        Decision trees that will allow rules to be applied in specific sequences and possible li
        ve updates depending on the decisions made to change the requirement. A feature to intro
        duce verification method should be incorporated. As a best practice all requirements wri
        tten typically include verification rational and a test plan, and the method selected wi
        ll inform how the requirement should be written.
    What did you not like about the prototype?
        It is very high friction. The current iteration will not be adopted by engineers unless 
        significant ease of use and installation features can be introduced (understandably diff
        icult). OpenAI integration didn't work. I didn't test LLama.
    What did you like about the assistant?
        The tool did reliably identify good requirement practices. Some of the suggestions were 
        solid, and even some suggestions brought insight into my own bad practices, like using o
        verly complex language.
    Any further comments for the research team?
        Notes (not generated): I used an AI generated ‘carboat’ requirement set made in ChatGPT 
        and evaluated with Claude Console. The suggestions to the base requirements were verbose
         and reasonable. Most seemed to pull from the requirement construct section of the ISO 2
        9148 standard, which I appreciated. I don’t believe INCOSE itself actually provides any 
        requirements standards, guidelines, or rules that weren’t first developed under ISO/IEEE
         as INCOSE is a guidance body rather than a standards body.  Some of the suggestions wer
        e repetitive with respect to the same requirement. The tool didn’t adequately capture th
        e dependencies between the conflicting suggestions, and accepting some changes would voi
        d or conflict with other suggested changes. I saw this occur with the tool trying to add
         multiple performance criteria or conditions to the requirement statement that would ult
        imately make it a bad requirement. The tool needs some feature to track which choices ar
        e made within the ruleset for each requirement evaluation. It may be an opportunity for 
        the tool to ‘regenerate’ suggests on the fly as specific choices are made. The tool coul
        d have a usability feature for mass selection of accept, modify, reject so users don’t n
        eed to click each box individually. I reviewed roughly 10 of the 35 requirements and cli
        cked reject on the rest.
